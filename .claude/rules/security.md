# Security and personal data

- Passwords hashed with argon2id; rate limits on signup, login and pack opening.
- Accounts (`src/lib/auth.ts`): Better Auth with e-mail and password, a confirmed address required before signing in, a public pseudo (unique whatever the case), a birth date (18+, checked in Paris time), terms acceptance stored in `consents`. Those checks run in a request hook before Better Auth, so a signup with a known address gets the same answer as any other (no account enumeration) and its owner gets an e-mail instead.
- Google sign-in (decided on 2026-10-24, for the Android app first; the site shows it too): Better Auth's `google` provider, on once `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are set (`src/lib/sign-in-methods.ts`; the forms hide the button otherwise). It asks for `openid` and `email` only, and keeps no Google token (an account hook nulls them). It never creates an account by itself (`disableImplicitSignUp`): the signup form's Google path sends the pseudo, birth date and terms with `requestSignUp`, the request hook checks them like an e-mail signup and stores them in the OAuth state's server context (`addOAuthServerContext`), and `mapProfileToUser` gives them to the new account on the callback, never Google's name or photo. Signing in with Google an address that has a confirmed account links Google to it. Google's errors come back to `/login` or `/signup` as `?error=` (`GoogleErrorNotice`); one with no message of its own shows its code underneath, with `?error_description=` when there is one (in the app, `app_sign_in_failed` and what the phone's sign-in said, or the code of a token the server refused), so that a player can quote it. A Google-only player has no password: `/account` offers a reset link to create one, and deletion asks for a session less than a day old instead of the password. Google refuses its sign-in page in the Android app's WebView: there, `continueWithGoogle()` asks the phone's own Google sign-in for an ID token issued to `GOOGLE_CLIENT_ID` and sends it to Better Auth (`idToken`), which checks it against Google's keys; a signup's checked pseudo and birth date wait in a request state (`inAppGoogleSignup`) instead of the OAuth state, and the outcomes go to the same addresses as the web flow's. At the app's first launch, the visitor home page offers the phone's Google accounts unasked (`GoogleAppPrompt`, once per install): an account with a World Up account is signed in, and one without goes to the signup form, which keeps the chosen account in memory (`heldGoogleAccount()`) and asks only for the pseudo, birth date and terms. That token carries Google's name and photo, dropped like on the web (`/privacy` says so).
- The forms call `/api/auth` from the browser (`src/lib/auth-client.ts`): Better Auth's rate limits apply to HTTP requests only, not to server-side `auth.api` calls. They are in memory (one web process) and key on the `X-Forwarded-For` header Traefik sets.
- Server components read the session with `getSession()` / `requireSession()` (`src/lib/session.ts`). `getAuth()` builds the auth instance on first use, since `next build` loads the modules without the runtime secrets.
- Sessions store no IP address or user agent (a database hook drops them).
- `/admin` requires two-factor authentication, and every back-office action writes to `audit_log`. The back-office account is the one whose e-mail is `ADMIN_EMAIL`; players get a 404. It sets up an authenticator app (Better Auth's `twoFactor` plugin, TOTP with backup codes, no "trust this device") at `/admin/two-factor`. A session hook sets `sessions.two_factor_verified` only on sessions created by a second-factor verification, and `requireAdmin()` (`src/lib/admin.ts`) demands it: an older session of the same account, opened before the app was set up, has to sign in again.
- Pages under `src/app/admin/(granted)/` and every server action call `requireAdmin()` themselves, since a layout is not rendered again on navigation. Catalogue changes go through `src/lib/catalog/admin.ts`, one transaction each with its `audit_log` row; showing or hiding a card renumbers the series.
- Collect only e-mail, birth date and purchase history, and keep personal data out of technical logs. Account export and deletion are self-service from `/account`.
- Retention (`src/lib/account-retention.ts`, the worker's daily `account-retention` job, scheduled by `createQueues()`): a signup never confirmed is deleted after 30 days; an account without a sign-in or session refresh (`users.last_active_at`, set by the session hooks) for 3 years is warned by e-mail, then deleted 30 days later unless the player comes back. `/privacy` states these periods: change both together.
- Terms of use: `TERMS_VERSION` (`src/lib/account-rules.ts`) is the date of the `/terms` text. `requireSession()` sends a player who has not accepted the current version to `/accept-terms`; `/account` passes `terms: false`, so a player who refuses can still export and delete. Bump the version whenever the text changes.
- The legal pages read the publisher's and host's details from the environment (`src/lib/publisher.ts`, documented in `.env.example`), and render at request time (`connection()`) so the server's values show. They must be filled before the site opens to the public.
- Multi-account detection uses the payment method and the normalised e-mail only: no device fingerprinting without consent. `users.email_normalized` is a generated column (lowercase, no "+tag", no dots for Gmail); `/admin/players` lists the accounts that share one, and a player's file there shows who they traded or dealt with most.
- Bans (`src/lib/players/admin.ts`, from `/admin/players/[id]`) set `users.banned_at`. Banning deletes the player's sessions, cancels their open trades (`cancelTradesOf()`) and the auctions they sell or lead, over or not (`cancelAuctionsOf()`, which tells the other player), and logs the reason in `audit_log`; the action e-mails it to them (`accountSuspended`), as `/terms` promises. The session-create hook refuses a banned account (`ACCOUNT_BANNED`, after the password check, so it reveals nothing) and `getSession()` ignores a session of one. Other players no longer see them (`findPlayer()`, the friends lists, the leaderboard); the back-office passes `{ banned: true }`. Cards and coins stay theirs; lifting the ban e-mails `accountRestored` and brings back nothing that was cancelled. The back-office account can't be banned.
- No advertising trackers; analytics must stay in the CNIL consent-exempt configuration, so an information banner is enough.
